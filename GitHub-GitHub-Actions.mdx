If your repositories are hosted on GitHub.com or GitHub Enterprise Cloud, this is the recommended setup. QA Wolf listens for the deployments your repository creates, and a [deployment trigger](/triggers/overview) decides which flows run for each one.

## Requirements

- Access to a QA Wolf workspace
- Admin access to the GitHub repository that deploys

## Connect QA Wolf to GitHub

<Steps>
  <Step title="Install the GitHub App">
    Enable the GitHub integration from **Workspace settings → Integrations**, which installs the QA Wolf GitHub App.
  </Step>
  <Step title="Select every repository that deploys">
    A repository the app does not cover sends no events, so the deploying repository has to be among the ones you select.
  </Step>
  <Step title="Confirm the connection">
    Reopen the integrations page and confirm GitHub is listed as connected.
  </Step>
</Steps>

## Emit deployments from your pipeline

QA Wolf fires on GitHub deployment records, not on workflow runs. Many hosting providers, Vercel among them, create those records already — check before adding anything.

If yours does not, your workflow creates the deployment and reports its success. [Report deployments to QA Wolf](/triggers/report-deployments#github) has the workflow, plus the two rules that decide whether a deploy lands where your triggers look: the environment name, and per-pull-request isolation for previews.

## Create a trigger

A connected integration does nothing on its own. Create a deployment trigger that matches the deployments you now emit, and name the flows it runs. See [Set up a trigger](/triggers/set-up-a-trigger).

## Verify

Push a commit and let it deploy. Confirm a new run appears in QA Wolf under the expected environment. When none does, [Diagnose a trigger](/triggers/diagnose-a-trigger) says whether the deployment arrived and which condition failed.
