QA Wolf runs flows against a real build of your app: an `.apk` or `.aab` for Android, an `.ipa` for iOS. Your pipeline uploads each new build and reports it as a deployment, and a [trigger](/triggers/overview) you create starts the runs. Every run records which build it installed.

<Check>
  Builds are turned on per workspace. Until they are on for yours, every upload fails with "Builds are not enabled for this workspace." Ask your QA Wolf representative to turn them on. Until then, follow [Legacy build uploads](/legacy-build-uploads).
</Check>

## How it works

<Steps>
  <Step title="Upload the build">
    Your pipeline uploads the file to an environment. QA Wolf reads the app id, version and build number from it, and returns a build id.
  </Step>
  <Step title="Report the deployment">
    Your pipeline calls `deployment.reportStatus` with the build id in `builds`.
  </Step>
  <Step title="A trigger matches">
    The deployment's first `success` report evaluates your triggers. Each one that matches creates a run, and the run installs the deployment's builds.
  </Step>
  <Step title="The flow launches the build">
    `launch({ app: { id } })` installs the run's build of that app.
  </Step>
</Steps>

<Warning>
  Uploading and reporting start nothing on their own. A workspace with no matching trigger records the deployment, runs nothing, and the pipeline step still succeeds. Create the trigger before you wire up the pipeline.
</Warning>

## Requirements

- An API key, created under **Workspace Settings → API Keys**. A workspace, organization or user key all work.
- The workspace id, shown on the same page.
- A QA Wolf environment to report into. The deploy resolves to an environment by alias or name, and a name that matches nothing creates a new environment that no trigger targets.
- One of: the [QA Wolf Fastlane plugin](https://github.com/qawolf/fastlane-plugin-qawolf) 1.2.0 or later, `qawolf/upload-build-action@v1` with `qawolf/notify-qawolf-on-deploy-action@v3` 3.2.0 or later, or `@qawolf/ci-sdk` 3.5.0 or later.
- `@qawolf/flows` 0.4.0 or later in your flows.

[Upload builds](/upload-builds) lists every other way to upload a build, including the Builds page, the CLI and Tester chat.

## Set up the pipeline

<Tabs>
  <Tab title="Fastlane">
    The plugin is not published to RubyGems, so point the `Gemfile` at the repository and pin a tag.

    ```ruby
    gem "fastlane-plugin-qawolf", git: "https://github.com/qawolf/fastlane-plugin-qawolf", tag: "1.2.0"
    ```

    Run `fastlane install_plugins`, then add both actions to the lane that builds your app. `upload_build_to_qawolf` uploads the file that `gradle` or `build_app` built. `notify_deploy_qawolf` reports the deployment with every build the lane uploaded.

    ```ruby expandable
    lane :qawolf do
      # Your existing build step, gradle for Android or build_app for iOS

      upload_build_to_qawolf(
        # Also read from QAWOLF_API_KEY and QAWOLF_WORKSPACE_ID
        qawolf_api_key: ENV.fetch("QAWOLF_API_KEY", nil),
        workspace_id: ENV.fetch("QAWOLF_WORKSPACE_ID", nil),
        # The environment whose runs install this build from now on
        environment: "Staging"
      )

      notify_deploy_qawolf(
        qawolf_api_key: ENV.fetch("QAWOLF_API_KEY", nil),
        workspace_id: ENV.fetch("QAWOLF_WORKSPACE_ID", nil),
        # The name or an alias of an environment that already exists
        environment: "Staging",
        # Which build this is, matched by a trigger's servicePattern
        service: "android"
      )
    end
    ```

    `notify_deploy_qawolf` reports a `success` status by default, which is the status that evaluates triggers. It sets `QAWOLF_DEPLOYMENT_ID` and `QAWOLF_ENVIRONMENT_RUNS_URL` in the lane context and the environment, and returns the deployment id. Runs start asynchronously afterwards, so no run id comes back.

    <Warning>
      A matrix over Android and iOS derives the same deployment identity for both legs, because no CI system exposes which leg is running. Reporting into one environment, the second leg starts nothing and the lane still goes green. Pass `provider_deployment_discriminator` on every job that deploys more than once at a time:

      ```ruby
      notify_deploy_qawolf(
        environment: "Staging",
        service: ENV.fetch("PLATFORM", nil),
        provider_deployment_discriminator: ENV.fetch("PLATFORM", nil)
      )
      ```
    </Warning>

    The plugin's [README](https://github.com/qawolf/fastlane-plugin-qawolf#builds) lists every option, including pull request environments.
  </Tab>

  <Tab title="GitHub Actions">
    Upload the build, then report the deployment with the upload step's `build-id` output.

    ```yaml expandable
    - name: Upload the build to QA Wolf
      id: upload-build
      uses: qawolf/upload-build-action@v1
      with:
        qawolf-api-key: ${{ secrets.QAWOLF_API_KEY }}
        workspace-id: ${{ vars.QAWOLF_WORKSPACE_ID }}
        input-file-path: ./path/to/app-release.apk
        environment: Staging

    - name: Report the deployment to QA Wolf
      uses: qawolf/notify-qawolf-on-deploy-action@v3
      with:
        qawolf-api-key: ${{ secrets.QAWOLF_API_KEY }}
        workspace-id: ${{ vars.QAWOLF_WORKSPACE_ID }}
        environment: Staging
        service: android
        builds: ${{ steps.upload-build.outputs.build-id }}
    ```

    Report each platform as its own deployment, with its own `service` and build, so each platform's trigger matches only its own build.

    <Warning>
      The action derives one deployment per workflow run, attempt, job and environment. Two legs of one matrix deploying the same environment therefore share a deployment, and only the first starts runs. Set `deployment-id` per leg to separate them.
    </Warning>

    `environment` names an existing QA Wolf environment. To test a pull request in its own ephemeral environment, name it in both steps, such as `pr-${{ github.event.pull_request.number }}`. On the upload step, also set `ephemeral-environment: "true"` and `base-environment`. See [PR testing](/deployment-testing/pr-testing).
  </Tab>

  <Tab title="Node.js">
    For a CI system that runs Node.js but is neither Fastlane nor GitHub Actions. Requires Node.js 24.14.1 or later, below 25.

    ```bash
    npm install @qawolf/ci-sdk
    ```

    ```javascript expandable
    import assert from "assert";
    import {
      detectProviderDeploymentId,
      makeQaWolfSdk,
    } from "@qawolf/ci-sdk";

    const apiKey = process.env.QAWOLF_API_KEY;
    assert(apiKey, "QAWOLF_API_KEY is required");

    const workspaceId = process.env.QAWOLF_WORKSPACE_ID;
    assert(workspaceId, "QAWOLF_WORKSPACE_ID is required");

    const { deployment, uploadBuild } = makeQaWolfSdk({ apiKey });

    const uploaded = await uploadBuild({
      filePath: "./path/to/app-release.apk",
      environment: { name: "Staging" },
      workspaceId,
    });
    if (uploaded.outcome !== "uploaded") {
      throw new Error(`Could not upload the build: ${JSON.stringify(uploaded)}`);
    }

    const detected = detectProviderDeploymentId({ discriminator: "android" });
    if (detected.outcome !== "detected") {
      throw new Error(`Could not identify this deployment: ${JSON.stringify(detected)}`);
    }

    const report = await deployment.reportStatus({
      workspaceId,
      providerDeploymentId: detected.id,
      status: "success",
      environment: { name: "Staging" },
      service: "android",
      builds: [uploaded.build.id],
    });
    if (report.outcome !== "reported") {
      throw new Error(`Failed to report the deployment: ${JSON.stringify(report)}`);
    }
    console.log(`Reported deployment ${report.deployment.id}: ${report.deployment.url}`);
    ```

    - `discriminator` separates the deployments one CI job makes at the same time, such as the legs of an Android and iOS matrix. Without it both legs derive the same identity, and only the first starts runs.
    - To block the pipeline on the result, add `deployment.waitForVerdict`. See [Node.js SDK](/deployment-testing/ci-sdk).
  </Tab>

  <Tab title="Webhook">
    For a pipeline that cannot run Node.js, such as ArgoCD, locked-down runners or minimal containers. Requires only HTTP requests.

    <Steps>
      <Step title="Upload the build">
        Request an upload URL, upload the file, and create the build. See [HTTP API](/upload-builds#http-api) for the three requests. Keep the `buildId`.
      </Step>

      <Step title="Report the deployment">
        ```bash expandable
        curl -X POST "https://app.qawolf.com/api/trpc/public.deployment.reportStatus" \
          -H "Authorization: Bearer $QAWOLF_API_KEY" \
          -H "Content-Type: application/json" \
          -d "{
            \"json\": {
              \"workspaceId\": \"$QAWOLF_WORKSPACE_ID\",
              \"providerDeploymentId\": \"$CI_BUILD_ID-android\",
              \"status\": \"success\",
              \"environment\": { \"name\": \"Staging\" },
              \"service\": \"android\",
              \"builds\": [\"$BUILD_ID\"]
            }
          }"
        ```

        `providerDeploymentId` is whatever your pipeline calls this build. It has to differ for every build, and for each leg of an Android and iOS matrix, because only a deployment's first `success` report evaluates triggers. See [Webhook](/deployment-testing/webhook) for every field and for the response shape.
      </Step>
    </Steps>
  </Tab>
</Tabs>

These examples upload an Android `.apk`. iOS works the same way: point the same steps at your `.ipa`, and name the service `ios`.

## Create a trigger

A deployment starts nothing until a trigger matches it. Create one on the workspace's triggers page, with conditions that match the deployments you now report:

| Condition | For a mobile pipeline |
| --- | --- |
| `environmentIds` or `environmentPattern` | The environment the build reports into. |
| `servicePattern` | `android` or `ios`, when both platforms report into one environment. A deployment that names no service never matches a trigger carrying a service pattern. |
| `branchPattern` | Narrow to the branch the build came from, when you report `metadata.ref`. |

Shipping both platforms into one environment needs two triggers, one per `servicePattern`, each selecting that platform's flows. Without the service condition both triggers fire on every deployment, so a new Android build also reruns the iOS flows on the environment's last iOS build.

`deployTargetPattern` matches on the deploy target URL, which a mobile build has none of, so it is not a way to tell builds apart.

See [Trigger fields](/triggers/reference) for every condition and for the action that selects which flows run.

<Tip>
  You can create and manage triggers from your own coding agent instead of the triggers page. Add the [QA Wolf MCP](/qawolf-mcp) and ask it to set up the triggers for your mobile environments. It can also list recent deployments and show why a trigger did or did not fire.
</Tip>

## Use the build in a flow

Name the app by its Android package name or iOS bundle id:

```ts
await launch({ app: { id: "com.example.app" } });
```

The flow installs the run's build of that app: the deployment's build, or else the environment's latest. Scheduled runs and runs started by hand install the environment's latest build, so they test the last upload too. See [How a run picks its build](/upload-builds#how-a-run-picks-its-build).

## Verify the integration

<Steps>
  <Step title="Run the pipeline">
    Run the CI job that builds your app.
  </Step>
  <Step title="Check the upload and the report">
    The upload step prints the build id. The report step logs the deployment id and the environment's runs page.
  </Step>
  <Step title="Check the trigger fired">
    Open the deployment in QA Wolf. It lists a verdict for every trigger, including the reason a trigger did not match. See [Deployments](/triggers/deployments#evaluation).
  </Step>
  <Step title="Check the run used the build">
    Open the run the trigger created. It shows the app version it tested, which matches the build you just uploaded.
  </Step>
</Steps>

## Troubleshooting

- **The upload fails with "Builds are not enabled for this workspace."** — builds are not on for your workspace yet. Ask your QA Wolf representative, and use [Legacy build uploads](/legacy-build-uploads) until then.
- **The upload is refused** — the file is not an `.apk`, `.aab` or `.ipa`, or is over 500 MB. If your pipeline zips the app, upload the file inside the zip.
- **The build uploads, the deployment is recorded, and nothing runs** — no trigger matched. Open the deployment and read the per-trigger verdicts. The usual causes are an environment name that created a new environment instead of resolving an existing one, and a `servicePattern` on the trigger that the report does not send a `service` for.
- **Only one of the two platforms runs** — both legs reported under the same `providerDeploymentId`, so the second updated the first deployment instead of creating one, and only a deployment's first `success` report evaluates triggers. Give each leg its own identity: `provider_deployment_discriminator` on Fastlane, `discriminator` on `detectProviderDeploymentId`, `deployment-id` on the GitHub Action.
- **One platform's build also reran the other platform's flows** — the triggers have no `servicePattern`, so both fire on every deployment. The other platform's flows install that environment's last build of their own platform.
- **`launch` fails with "No build of … on this environment"** — the run has no build of that app. Check that the `id` in `launch` matches the build's app id, and that the build was uploaded to this environment or reported with the deployment. A build whose file expired counts as absent.
- **The run installed an old file, or shows no app version** — the flow calls `launch()` with no `app`, or with `app: { path }` or `app: { env }`, so it reads `RUN_INPUT_PATH` or a fixed file. Change it to `launch({ app: { id } })`. See [Move from legacy uploads](/upload-builds#move-from-legacy-uploads).
- **The pipeline step passes but the workspace never sees the deploy** — the step is still on the legacy deploy webhook. `@v1` and `@v2` of the notify action, Fastlane plugin 0.4.8 and below, and the SDK's `attemptNotifyDeploy` all report through it, and triggers never see it.
- **Authentication errors** — check `QAWOLF_API_KEY`, and that `workspaceId` names the workspace the key may act on.
