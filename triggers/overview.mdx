A loop tells QA Wolf what to do when something happens. It has two parts:

- **When** — what starts the loop: a deploy, a schedule, or a pull request.
- **Then** — what QA Wolf does each time: **Run AI** with your instructions, or **Run specific flows**.

Loops belong to the workspace, so one loop can cover staging, production, and every preview environment. You find them under **Loops** in the main navigation. The public API and CLI call a loop a trigger, through `trigger.*`. See [Trigger fields](/triggers/reference).

## When

The **Starts on** menu picks what starts the loop:

- **Deploys to an environment** — fires when your pipeline notifies QA Wolf of a successful deploy to staging, production, or any long-lived environment. See [PR testing](/deployment-testing/pr-testing) and the deployment testing guides for how the notification reaches QA Wolf.
- **A schedule** — fires in one environment every few hours, days, weeks, or months. Pick a shortcut such as **Hourly**, **Weekdays**, or **Every 2 weeks**, or set **Every [N] [unit] at [time]**. An hourly or daily schedule can be restricted to chosen days of the week. Needs nothing from your pipeline.
- **Pull request previews** — fires on deploys to preview environments named like a pattern, such as `pr-*`.
- **A pull request** — fires when a pull request in a repository is opened, marked ready for review, gets new commits, gets a label, or is merged. Needs a connected GitHub or GitLab integration. Not every workspace has it yet.

To narrow a deploy loop, select **Only when…** and add a repository, service, branch, or deploy URL condition. Each condition suggests the values your recent deploys reported, and you can type a name or [pattern](/triggers/reference#deployment-conditions) instead. The editor says how many of your recent deploys the loop would have run on, and lists them.

## Then

- **Run AI** — starts a QA Wolf AI session with the instructions you write. See [Run AI](/triggers/run-ai).
- **Run specific flows** — runs the flows you pick. Select tags, flows named one by one, or both. Flows tagged later join automatically.

**Run options** holds failure investigation and the number of flows that run in parallel. Run AI has no run options.

A [Smart Smoke Suite](/smart-smoke-suites) lets QA Wolf choose the flows from the change behind each deploy. Choose **Run AI** and start the instructions with `/smart-smoke-suite`. It works only on a loop that starts on a deploy.

Give preview deploys their own loop rather than widening the one that covers staging. A pull request rarely needs everything staging runs.

## Create a loop

On the Loops page, select **New loop**. Pick a template, such as **Nightly regression** or **Test each pull request**, or select **Go lone wolf** to start blank. Name the loop, fill in **When** and **Then**, and select **Create loop**.

**Create loop** stays disabled until the loop is complete, and says what is missing.

## Run now

**Run now** fires a loop by hand, so you can try it before it fires on its own. It sits on each row of the Loops page and on the loop's own page.

- **A schedule loop** fires at once, in its environment.
- **A deploy loop** opens a menu of recent deploys the loop matches. Pick one, and the loop fires on it, in that deploy's environment.

Run now works on a paused loop. It is not available for a Smart Smoke Suite or a pull request loop.

## Run history

A loop's page shows **Run history**, one row per firing, newest first. A row says whether the loop fired, what happened, and when. A firing started with Run now says who started it.

- **A run** — opens into its results.
- **A session** — shows whether it is working, finished, failed, or waiting for its owner. It opens into the session's latest reply, how long it worked, the flow it left if any, and **Open in chat**.
- **A skipped firing** — says why nothing started, such as "This loop has no owner on the team to run the session as".

## Mobile apps

A mobile pipeline uploads each new build and reports it as a deployment. The runs a deploy loop starts install that build. A scheduled run installs the environment's latest build. When Android and iOS both report into one environment, give each platform its own loop with a service condition. See [Mobile build testing](/mobile-build-testing).

## Pausing

The **Enabled** switch on a loop's page pauses and resumes it. A paused loop never fires on its own. Resuming brings back the same configuration. A resumed schedule picks up at its next slot, and slots it missed while paused don't run.
