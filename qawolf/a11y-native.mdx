## Overview

QA Wolf supports accessibility (a11y) testing for native iOS and Android apps via **WebdriverIO** with the **Appium plugin**. This is different from web-based a11y testing, where a rules engine like axe-core scans the DOM. Native apps don't have a DOM, so instead tests verify that key screens are **automatable via accessibility semantics**: labels and IDs that the OS exposes to VoiceOver (iOS) and TalkBack (Android).

If your test can locate and interact with an element via its accessibility label, a screen reader can too. This makes accessibility-ID-based testing a strong proxy for accessibility hygiene on native screens.

<Note>
  This page covers native iOS and Android apps only. For mobile web or any web page, see [Axe-core Scanning](#) and [Lighthouse Accessibility Reports](#) instead.
</Note>

## How It Works

Tests locate elements using **accessibility identifiers** — attributes set by your developers that expose UI components to the OS accessibility layer.

| Platform | Attribute | WebdriverIO Selector |
| --- | --- | --- |
| Android | `content-desc` | `driver.$('~your-label')` |
| iOS | `accessibilityIdentifier` / accessible `name` | `driver.$('~your-id')` |

The `~` prefix is the WebdriverIO shorthand for locating an element by its accessibility ID. This is a "double win": it proves the element is correctly exposed to the accessibility layer, and it keeps your tests stable across visual refactors.

## Patterns

### Pattern 1: Locate by Accessibility ID and Assert Usability

The most fundamental a11y check: prove that a screen's key elements are reachable and usable through accessibility semantics alone.

```ts
// Example: login screen a11y readiness
const email = await driver.$("~Email");       // accessibility id
const password = await driver.$("~Password"); // accessibility id
const loginBtn = await driver.$("~Log in");   // accessibility id

await expect(email).toBeDisplayed();
await expect(password).toBeDisplayed();
await expect(loginBtn).toBeEnabled();

await email.setValue(process.env.USER_EMAIL);
await password.setValue(process.env.USER_PASSWORD);
await loginBtn.click();

// Assert the next screen is also reachable via accessibility labels
const homeHeader = await driver.$("~Home");
await expect(homeHeader).toBeDisplayed();
```

<Tip>
  If you can't locate an element using `~`, that element is likely missing an accessibility label entirely — an accessibility bug worth raising with your dev team before writing the test.
</Tip>

---

### Pattern 2: Assert Icon Buttons Have Meaningful Accessible Names

Icon-only buttons — hamburger menus, close buttons, search icons — must have a meaningful accessible name, or screen reader users won't know what they do. Use `content-desc` on Android to assert the label exists and is non-trivial.

```ts
const menuIcon = await driver.$("~Main menu"); // content-desc / accessibility id
await expect(menuIcon).toBeDisplayed();

// Verify the label isn't blank or too short to be meaningful
const label = await menuIcon.getAttribute("content-desc");
if (!label || label.trim().length < 3) {
  throw new Error("A11y: menu icon accessible label is missing or too short");
}
```

## What's Not Included

<Warning>
  QA Wolf does not run a WCAG rules engine against native app views. Native apps don't have a DOM, so axe-core style scanning isn't available for native iOS or Android.
</Warning>

For deeper audits — color contrast, touch target size, reading order — supplement these tests with manual testing:

- **VoiceOver** on iOS
- **TalkBack** on Android
- **Xcode Accessibility Inspector** or **Android Studio Layout Inspector**

## Quick Reference

| Goal | How to do it |
| --- | --- |
| Prove an element is on the accessibility layer | Locate it with `driver.$('~accessibility-id')` |
| Assert a screen is navigable via accessibility semantics | Use `~` selectors throughout the full flow |
| Assert an icon button has a meaningful label | `getAttribute('content-desc')` and check length |
| Assert an error or toast is readable | `await expect($('~error-id')).toHaveText('...')` |
| Full WCAG audit | Pair these tests with manual VoiceOver / TalkBack sessions |
