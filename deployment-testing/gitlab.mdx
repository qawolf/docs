GitLab creates a deployment whenever a job declares an `environment:`. QA Wolf receives those deployments through the connected integration, and a [trigger](/triggers/overview) decides which flows run for each one.

## Requirements

- Access to a QA Wolf workspace with at least one environment
- Maintainer access to the GitLab group that owns the deploying project

## Connect GitLab

<Steps>
  <Step title="Create a group access token">
    The token needs the **Maintainer** role and the `api` scope. QA Wolf refuses anything lower, because a lesser role cannot create the webhooks it reads deployments from.
  </Step>
  <Step title="Enable the GitLab integration">
    Paste the token into **Workspace settings → Integrations**. QA Wolf can then read deployments, set commit statuses, and link runs to GitLab commits.
  </Step>
</Steps>

## Declare an environment on your deploy job

A job with the `environment:` keyword creates the deployment, and the webhook fires when the job succeeds. Nothing else is required of the pipeline.

[Report deployments to QA Wolf](/triggers/report-deployments#gitlab) has the job, along with the two facts that decide whether a deploy lands where your triggers look:

- **The environment name** — QA Wolf matches it against the workspace's environments by alias or by slugified name, and creates a new environment when nothing matches.
- **The `review/` prefix** — GitLab has no transient flag, so the name is what marks a preview environment short-lived. A preview named anything else accumulates permanently.

<Warning>
  A preview environment also needs a per-merge-request URL. With a shared URL the trigger still matches and the run executes against whatever was deployed last, which produces a green run for code that was never exercised.
</Warning>

## Test every merge request

A preview deploy gives QA Wolf a deployment that resolves to the merge request it came from, which is what makes pull-request testing possible. Two things have to hold, both covered in [Report deployments to QA Wolf](/triggers/report-deployments#isolate-previews-per-pull-request): the deployment names an environment unique to the merge request, and its URL is unique too.

Give previews their own trigger rather than widening the one that covers staging. Match the shape your pipeline emits — `review/*` — and choose what runs:

- **A small tag**, for a fixed set of fast flows on every pull request.
- **[Generative flow selection](/triggers/overview#generative-flow-selection)**, which lets QA Wolf pick the flows from the pull request itself. It needs the deployment to resolve to a pull request, so it fits a preview trigger and skips any deployment without one.

## Create a trigger

A connected integration starts no runs on its own. Create a deployment trigger whose conditions match the deployments you now emit, and name the flows it runs. See [Set up a trigger](/triggers/set-up-a-trigger).
