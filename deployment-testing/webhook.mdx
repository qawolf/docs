When your pipeline cannot create a GitHub or GitLab deployment, it can notify QA Wolf of the deploy itself. The `deployment.reportStatus` route takes the same information a deployment event carries, and a [trigger](/triggers/overview) evaluates it the same way.

Pick this path when your code host is not GitHub or GitLab, when the deploying repository is not connected, or when the deploy happens somewhere your code host never sees. A pipeline that runs Node.js can make the same report through the [Node.js SDK](/deployment-testing/ci-sdk), which also waits for the verdict.

## Requirements

- An API key, created under **Workspace Settings → API Keys**. A workspace, organization or user key all work. A workspace key reports into its own workspace, so `workspaceId` has to name that workspace.
- The ability to make an authenticated HTTPS request from your pipeline.

## What a report carries

| Field | Description |
| --- | --- |
| `workspaceId` | The workspace to report the deployment into. |
| `providerDeploymentId` | Your identifier for the deployment. Reports carrying the same one update a single deployment. |
| `status` | `pending`, `success`, `failure` or `inactive`. |
| `environment` | Required on the first report for a `providerDeploymentId`. Either `{ id }` for an existing environment, or `{ name }`, which resolves by alias or name and creates an environment when nothing matches. A `{ name }` selector also takes `ephemeral` and `baseEphemeralEnvironment`. |
| `environment.ephemeral` | `true` for a preview deploy. Defaults to `false`, which creates a permanent environment. A name that matches an existing environment keeps that environment's kind. |
| `environment.baseEphemeralEnvironment` | The alias or name of the environment a created ephemeral environment copies from. Only valid with `ephemeral: true`. Defaults to the environment for the pull request's base branch, then to the workspace's base environment. |
| `deployTarget` | The URL the deployment serves, as an `http` or `https` URL. Required when `environment.name` names no existing environment; a report that would create one without it is refused. |
| `environmentVariables` | Overrides for the runs this deployment requests, as a flat map of string to string. A report that sends them replaces the stored values; one that omits them keeps them. |
| `service` | Which application was deployed, such as `checkout-api`, when several applications deploy into one environment, or when one pipeline ships more than one build such as an Android and an iOS build. A trigger's `servicePattern` matches on it. A report that omits it keeps the stored value. |
| `builds` | The ids of the [builds](/upload-builds) this deployment ships, at most 20. The runs this deployment starts install them. A report that omits it keeps the stored builds. |
| `metadata` | Details about the deployed revision, such as the commit. |
| `changes` | What the deployment changed, for a [Smart Smoke Suite](/smart-smoke-suites) on a deploy with no pull request. See [Changes](#changes). |

<Warning>
  Send `environment.ephemeral: true` for every preview deploy. A report that omits it is accepted and creates a permanent environment, one per pull request, that is never torn down.
</Warning>

Example:

```json
"environment": { "name": "preview/pr-42", "ephemeral": true }
```

## The request

Example:

```bash
curl -X POST "https://app.qawolf.com/api/trpc/public.deployment.reportStatus" \
  -H "Authorization: Bearer $QAWOLF_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"json\": {
      \"workspaceId\": \"$QAWOLF_WORKSPACE_ID\",
      \"providerDeploymentId\": \"$DEPLOY_ID\",
      \"status\": \"success\",
      \"environment\": { \"name\": \"staging\" },
      \"deployTarget\": \"https://staging.example.com\",
      \"metadata\": { \"commitSha\": \"$GIT_COMMIT_SHA\", \"ref\": \"$GIT_BRANCH\" }
    }
  }"
```

The input goes inside a `json` wrapper, and the reply carries the deployment under `result.data.json`. Replace `$DEPLOY_ID` with whatever your pipeline calls this deploy — a build number or a pipeline id — and `$QAWOLF_WORKSPACE_ID` with the id from **Workspace Settings → API Keys**.

### Metadata

`metadata` describes the revision you deployed. Every field is optional, and each one QA Wolf receives makes the deployment easier to recognize and to link back to your code.

| Field | Description |
| --- | --- |
| `commitSha` | The commit sha of the deployed revision. |
| `ref` | The branch or ref that was deployed. |
| `repository` | The `owner/name` of the repository, such as `acme/web`. A trigger's `repositoryPattern` matches it even when the repository isn't connected. |
| `pullRequestNumber` | The pull request the deployment belongs to. Requires `repository`, and a connected integration covering that repository. Without it, `repository` and `commitSha` find the pull request from the commit. |
| `commitUrl` | A link to the deployed commit, as an `http` or `https` URL. |
| `commitMessage` | The deployed commit's message. The deployments list shows its first line. |
| `commitAuthorName` | The display name of the commit's author. |

<Warning>
  `repository` and `pullRequestNumber` only link the deployment to its pull request when a connected GitHub or GitLab integration covers that repository. QA Wolf reads the pull request from the code host. Without the integration the report succeeds and the deployment carries no pull request. See [PR testing](/deployment-testing/pr-testing).
</Warning>

### Changes

`changes` tells a [Smart Smoke Suite](/smart-smoke-suites) what a deploy with no pull request shipped: each merged pull request or pushed commit, plus release notes. It takes readable text only. There is no field for diffs or file contents, and unknown fields are refused.

| Field | Description |
| --- | --- |
| `items` | The pull requests and commits the deployment ships, newest first. At most 250. |
| `items[].kind` | `pull-request` for a merged pull request, `commit` for a commit pushed without one. Required. |
| `items[].title` | The pull request title or the commit subject. Required. At most 512 characters. |
| `items[].description` | The pull request description or the commit message body. Put ticket ids here or in the title. At most 4,000 characters. |
| `items[].changedPaths` | Paths of the files the change touched, without their contents. At most 1,000 paths of up to 1,024 characters each. |
| `items[].url` | A link to the pull request or commit, as an `http` or `https` URL. At most 2,048 characters. |
| `omittedCount` | How many pull requests or commits you left out of `items` to stay within the limits. |
| `releaseNotes` | Release notes written for the deployment. At most 16,000 characters. |

The whole `changes` value is at most 256 KB. Text fields are trimmed, and a field that's empty after trimming is refused.

- A report that omits `changes` keeps the stored value. A report that sends it replaces it.
- A value with no `items` and no `releaseNotes` counts as not sent.
- Triggers read it on the deployment's first `success` report, so send it on that report or an earlier one.

Example:

```json
"changes": {
  "items": [
    {
      "kind": "pull-request",
      "title": "Recalculate the cart total with discounts",
      "description": "Fixes SHOP-123. Discounts now apply before tax.",
      "changedPaths": ["src/checkout/cartTotal.ts"],
      "url": "https://git.example.com/acme/web/pull/42"
    },
    { "kind": "commit", "title": "Bump the payment SDK" }
  ],
  "releaseNotes": "Checkout shows discounted totals."
}
```

From a Node.js pipeline, `deployment.collectCommitChanges` in `@qawolf/ci-sdk` builds this value from your git history. See [Sending changes from your CI](/smart-smoke-suites#sending-changes-from-your-ci).

## When a report starts a run

- A deployment's first `success` report evaluates triggers, and it is the only report that does. To evaluate a deploy again, report it under a new `providerDeploymentId`.
- The response carries the deployment only, never the resulting runs.
- A deployment stays bound to the environment resolved on its first report, so later reports may omit the selector. Report a promotion as a new deployment under a new `providerDeploymentId`.

How the environment name resolves, and what a preview deploy needs, is covered in [Deployments](/triggers/deployments).

## Create a trigger

Reporting a deploy starts nothing on its own. Create a deployment trigger whose conditions match the deployments you now report. See [Triggers](/triggers/overview).
